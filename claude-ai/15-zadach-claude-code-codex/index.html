Пошаговая инструкция

Если начать с команды «сделай приложение», агент быстро напишет код, но тебе придётся угадывать, что он решил за тебя. Здесь работа устроена наоборот: сначала записываем результат, затем шаг за шагом уменьшаем число догадок. Так легче остановить ошибку до того, как она разойдётся по проекту

Это 15 готовых промптов для Claude Code и Codex. Во всех уже указан один пример: локальное веб-приложение «Список дел» с тестовой базой SQLite, то есть отдельным файлом с учебными задачами. Эти промпты проводят учебный проект от требований до сквозной проверки и помогают сохранить инструкцию для повторной приёмки

Задача 1 из 15

Описать требования как наблюдаемый результат

до первого файла с кодом, когда идея пока звучит одной фразой

Мы делаем локальное веб-приложение «Список дел». Пользователь должен создавать задачу, менять её текст, отмечать выполненной, возвращать в работу и удалять после отдельного подтверждения. Данные хранятся в SQLite. Авторизации, совместной работы и уведомлений в первой версии нет.

До написания кода создай документ требований. Для каждой функции напиши: что должно произойти и как это проверить. Добавь границы первой версии, состояния ошибки, правила для пустого названия и критерии приёмки. Не придумывай требования молча: спорные решения вынеси в раздел «Допущения»

документ с функциями, границами и проверяемыми критериями приёмки

у каждого требования есть наблюдаемое действие и однозначный признак успеха

Задача 2 из 15

Записать правила проекта в действующий файл

когда одни и те же ограничения приходится повторять в каждом чате

Проверь, есть ли AGENTS.md в корне учебной копии проекта. Если есть, используй его как файл правил и покажи, какие правила уже действуют. Если файла нет, предложи создать один AGENTS.md в корне, сначала покажи его полный текст и только после моего подтверждения создай файл. Не создавай CLAUDE.md или второй файл с теми же правилами. Если другой файл уже имеет приоритет, остановись и опиши конфликт без изменений.

Подготовь правила для AGENTS.md: сохранять пользовательские изменения, сначала читать требования, считать задачу выполненной только после проверки, не включать секреты в код, операции с базой и удалением показывать только на тестовой копии, а перед git-коммитом показывать точный diff. Сначала покажи предлагаемую правку или полный текст нового файла. После моего подтверждения внеси её и покажи полный diff файла

один источник правил без правил-дублей

AGENTS.md есть в корне, а полный diff не содержит удаления прежних правил

Задача 3 из 15

Сначала составить план, не меняя файлы

когда затронуто несколько частей проекта или цена ошибки выше пары минут

Работай только в режиме планирования и пока не меняй файлы. Изучи структуру проекта «Список дел», действующие правила и документ требований. Проверь, ведётся ли здесь история Git. Если да, сохрани исходный вывод `git status --short`, чтобы отличить прежние изменения от новых. Если нет, напиши «Git пока не настроен» и не запускай команды Git.

Предложи три варианта реализации: минимальный, обычный и расширенный. Для каждого укажи затрагиваемые файлы, проверки, риск и объём. Выбери один вариант и объясни выбор. Финал плана: последовательность шагов, после каждого шага указан способ проверки

выбранный маршрут с файлами, рисками и проверками

план готов, но на этом шаге агент не менял файлы

Задача 4 из 15

Разрабатывать по спецификации, а не по догадке

после согласования требований и перед реализацией первой функции

Возьми документ требований приложения «Список дел» как контракт. Составь таблицу: критерий приёмки, изменение в коде, автоматическая проверка, ручная проверка.

Пока не меняй код. Для каждого критерия первой версии укажи планируемый файл, способ реализации, автоматическую проверку и ручную проверку. Не добавляй авторизацию, уведомления и совместную работу. Если какой-то критерий нельзя связать с проверкой, пометь пробел и остановись до уточнения

карта реализации без функций, которых не просили

каждый критерий связан с будущим изменением и способом проверки

Задача 5 из 15

Подготовить бриф интерфейса до вёрстки

когда экран уже понятен по функциям, но ещё не по состояниям и поведению

Подготовь бриф интерфейса для приложения «Список дел». Главный экран должен работать на телефоне шириной 360 пикселей и на ноутбуке.

Опиши иерархию экрана, тексты кнопок, пустое состояние, загрузку, ошибку сохранения и успешное действие. Добавь работу с клавиатуры, заметный фокус, достаточный контраст и подтверждение удаления. Не рисуй декоративные блоки без функции. Заверши списком визуальных критериев, которые можно проверить в браузере

бриф всех состояний одного экрана

есть мобильный вид, клавиатура, ошибки, пустота и подтверждение удаления

Задача 6 из 15

Разбить реализацию на маленькие проверяемые шаги

когда план всё ещё слишком крупный для безопасной работы

Разбей реализацию приложения «Список дел» на шаги длительностью до одного логического изменения: схема данных, создание задачи, редактирование, смена статуса, удаление с подтверждением, адаптивный интерфейс, итоговые тесты.

Для каждого шага укажи входные файлы, ожидаемый результат, команду проверки и условие остановки. Не смешивай рефакторинг и новую функцию в одном шаге. Сначала покажи весь порядок. После моего явного подтверждения выполняй строго по одному шагу только в учебной копии. Для хранения данных используй лишь тестовую базу `./tmp/tasks-test.sqlite`; её схему и тестовые записи настроим отдельным шагом. Останавливайся на первой красной проверке. В конце покажи, как запустить работающую учебную версию, прежде чем переходить к проверке браузера

Задача 8 из 15

Настроить базу только на тестовых данных

когда функция сохраняет, меняет или удаляет записи

Работай только с тестовой базой `./tmp/tasks-test.sqlite`, которую указали в плане реализации. Если файла ещё нет, создай его только в учебной копии проекта. Не открывай и не меняй рабочую базу, даже если найдёшь её в проекте.

Примени существующую миграцию к тестовой базе. Если миграции ещё нет, создай её со схемой id, title, status, created_at и updated_at. Добавь пять тестовых записей и проверки создания, чтения, изменения статуса и удаления. Пустой title должен отклоняться. Покажи абсолютный путь тестовой базы и команду проверки. Не удаляй файл: сначала покажи точный путь и дождись отдельного подтверждения именно этого пути

воспроизводимая схема и тестовый набор данных

Осторожно: сначала сверяй абсолютный путь. Удалять можно только созданный в этой задаче тестовый файл после отдельного подтверждения пути

Задача 9 из 15

Проверить риски безопасности без ложной гарантии

после работающей функции и ещё раз после исправления найденных проблем. До обзора проверь, что ключи и токены не попали в проект

Проведи обзор безопасности учебного приложения «Список дел». Проверь обработку пользовательского текста, SQL-запросы, вывод данных в HTML, секреты в репозитории, зависимости и доступ к файлам.

Для каждой находки укажи серьёзность, точный файл и строку, возможное последствие и минимальное исправление. Значения секретов не печатай: показывай только тип, имя и путь с маскировкой. Доказательство выбирай безопасное для типа находки: тест, вывод сканера или официальный бюллетень. Не запускай разрушительный сценарий. Отдели подтверждённые проблемы от предположений. После исправлений повтори проверки. В выводе укажи ограничения обзора и не утверждай, что он доказывает полную безопасность

список находок с безопасными доказательствами и ограничениями

для каждой подтверждённой проблемы есть подходящая улика до исправления и чистая повторная проверка после

Безопасная граница: зелёный обзор снижает известные риски, но не доказывает отсутствие всех уязвимостей

Задача 10 из 15

Найти причину ошибки до исправления

если появилась повторяемая ошибка. Пример ниже условный: считай ошибку подтверждённой только если она появилась у тебя на экране

Проверь условный сценарий: в мобильном браузере дважды нажми «Выполнено». Если появилась ошибка 500, запиши её фактический текст, время и точные шаги. Если ошибки нет, не называй её наблюдаемой и не придумывай журнал. Не исправляй код, пока проблема не воспроизведена.

Попробуй воспроизвести ошибку пять раз. Если она не повторилась, ничего не исправляй: верни журнал попыток и список недостающих данных. Если повторилась, прочитай фактический журнал ошибки, найди путь данных от кнопки до записи в тестовой базе и сформулируй одну проверяемую гипотезу. Создай регрессионный тест, добейся красного результата, внеси одно исправление и повтори весь набор тестов

причина и точечное исправление либо доказательный отчёт о невоспроизводимости

есть пять попыток, а при исправлении новый тест красный до правки и зелёный после

Задача 11 из 15

Проверить пользовательские сценарии целиком

когда отдельные функции уже работают, но важно проверить путь человека от начала до результата

Запусти приложение с временной тестовой базой и проверь в браузере четыре сценария:
1. Пустой список → создание задачи «Купить молоко» → задача видна после перезагрузки
2. Редактирование текста на «Купить овсяное молоко» → новый текст сохраняется
3. Отметка выполненной → возврат в работу
4. Удаление → отмена в подтверждении → повторное удаление → задача исчезла

Проверь ширину 360 и 1280 пикселей и управление клавиатурой. В тестовой среде подмени один ответ сохранения на 500 и проверь, что интерфейс показывает понятную ошибку без потери введённого текста. Для каждого сценария сохрани статус «прошёл» или «не прошёл» и точку отказа

отчёт о четырёх путях и безопасной проверке состояния ошибки

отчёт содержит действие, ожидаемое поведение, фактический результат и статус каждого сценария

Задача 12 из 15

Убрать лишний код без слепого удаления

после изменения архитектуры или завершения крупной функции

Работай в отдельной учебной копии приложения «Список дел». Сначала только составь список кандидатов на удаление: неиспользуемые файлы, импорты, функции и стили.

Для каждого кандидата покажи доказательство: поиск ссылок, результат анализатора, конфигурацию, маршруты, динамические импорты и затрагиваемые тесты. Ничего не удаляй до таблицы кандидатов. Перед удалением сохрани неизменённую учебную копию для сравнения. После моего отдельного подтверждения удали только позиции из согласованного списка. Если история Git есть, покажи `git diff`; если её нет, перечисли точные удалённые строки и файлы, сверив две учебные копии. Затем собери проект и запусти полный набор тестов и браузерные сценарии

у каждого удаления есть доказательство, сборка, тесты и сценарии остаются зелёными

Перед запуском: удаление выполняется только в отдельной учебной копии после просмотра списка кандидатов

Задача 13 из 15

Разделить изменения на понятные сохранения в истории проекта

когда изменения проверены и их нужно разделить на читаемую историю

Работай только в учебной копии проекта. Сначала проверь, ведётся ли здесь история Git. Если нет, покажи путь учебной папки и предложи настроить историю версий только в ней. До моего отдельного подтверждения ничего не настраивай. Если я подтвержу настройку, покажи полный список файлов и предложи один начальный коммит: прежние изменения нельзя задним числом честно разделить на этапы. Создай его только после отдельного подтверждения состава файлов. Если я не подтвержу настройку, пропусти эту задачу и объясни, что остальные проверки можно выполнить без истории версий. Если история уже была до этой задачи, покажи `git status`, полный `git diff` и список файлов, созданных именно в этой задаче. Не включай чужие или прежние изменения.

Только если история уже была, раздели новые изменения максимум на три атомарных коммита по фактическим границам: требования и план, реализация списка задач, тесты и документация. Не создавай пустые коммиты и не дроби связанное изменение ради количества. Для каждого предложи точный состав файлов и сообщение на русском. Перед созданием каждого коммита ещё раз покажи staged diff. Не выполняй push и не переписывай историю

если история уже была - согласованные сохранения; если нет - начальное сохранение либо честный пропуск

состав сохранений согласован заранее либо записано решение работать без истории версий

Только на копии: учебный пример не выполняет push, force push, reset или очистку рабочего дерева

Задача 14 из 15

Настроить автоматические проверки

когда одна и та же ошибка возвращается из-за пропущенного теста или проверки

Изучи, какие автоматические проверки уже есть в учебной копии проекта «Список дел», и проверь, настроена ли история Git. Если истории нет, настрой только местные команды форматирования и тестов; проверку перед сохранением версии и удалённую автоматическую сборку проекта (CI) отложи. Без подтверждения историю не создавай. Если история есть, предложи минимальную схему: форматирование и быстрые тесты перед сохранением версии. Для CI сначала выясни, есть ли удалённый репозиторий и подходящий сервис. Если их нет, подготовь только конфигурацию для будущего запуска и не называй CI работающим. Отправку проекта в сеть (push) не выполняй.

Сначала прочитай правила выбранного инструмента: разные проверки могут останавливать разные действия. Настрой доступные проверки только в копии. Покажи человеку, где лежат файлы настроек и какую кнопку или команду нажать для местной проверки. Запусти её без отправки проекта: на экране должен появиться отчёт с зелёным статусом. Затем намеренно создай безопасную ошибку форматирования и падающий тест в копии, покажи красный отчёт и верни файлы в зелёное состояние. Проверку перед сохранением версии считай работающей только после её отдельного запуска. CI считай работающим только после реального отчёта в удалённом сервисе; без него укажи «конфигурация подготовлена, запуск не проверен»

проверенные местные команды и честный статус настройки дополнительных проверок

Оформить повторяемую работу в скилл

когда одна процедура уже повторилась несколько раз и её шаги стабилизировались. Перед сборкой посмотри пять примеров готовых скиллов

В учебной копии проекта оформи повторяемую приёмку функции в скилл `priemka-fichi`. Сначала найди действующий формат скиллов в этой среде и не изобретай второй формат.

Задай корректные `name` и `description`, чтобы скилл можно было найти по просьбе «проверь готовность функции». Вход: документ требований, текущие файлы функции и тесты; список изменений приложи, если он доступен. При наличии Git проверь `git diff` и историю коммитов, без Git сравни сохранённые учебные копии, если они есть. Пустой или неполный список изменений не считай доказательством готовности и не выдумывай отсутствующий diff. Шаги: сопоставить критерии с текущими файлами, запустить тесты, проверить пользовательский сценарий, отделить подтверждённые дефекты от предположений, выдать статус каждого гейта. Выход: короткий отчёт с уликами. Добавь запрет на удаление, работу с рабочей базой и git push. Сначала запусти скилл по имени для функции «создание задачи», затем повтори проверку обычной фразой «проверь готовность функции» и отдельно зафиксируй результат каждого запуска
